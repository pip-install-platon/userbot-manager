# userbot-manager

Каркас маршрутизации личных сообщений Telegram между клиентами и операторами. Юзербот (Pyrogram, MTProto) и админ-бот (aiogram 3) не вызывают друг друга: общая библиотека `core` хранит данные в PostgreSQL, статусы и события — в Redis. История и анкета в базе лежат только в виде AES-GCM шифротекста ключа конкретного оператора.

Лицензия: GPL-3.0. Файл `LICENSE`.

## Состав

- `userbot` слушает личные сообщения аккаунта-приёмника, назначает свободного оператора и пересылает реплики.
- `admin_bot` — интерфейс оператора: статус, анкета, свои диалоги, супер-админ.
- `core` — модели, репозитории, криптография, роутинг, шина событий.
- `postgres` и `redis` поднимаются через Docker Compose.

Один клиент закреплён за одним оператором. Оператор читает только свои диалоги: выборка всегда фильтруется по `operator_id`, расшифровка выполняется только для авторизованного оператора. Массовой рассылки нет.

`file_id` у MTProto и Bot API не совпадают. Байты вложения на время доставки кладутся в Redis (`media:{uuid}`, TTL 1 час; файлы анкеты — `profile_media:{id}`). В PostgreSQL сохраняется исходный `file_id`, не расшифрованный текст.

События между процессами идут по Redis Pub/Sub внутри сети Compose. В каналах ответа клиенту есть текст сообщения: это транспорт между своими процессами, а не хранилище. В таблице `messages` лежит только шифротекст. Redis не должен быть опубликован наружу; в Compose порты привязаны к `127.0.0.1`.

## Требования

- Docker и Docker Compose, либо локально Python 3.12, PostgreSQL 16 и Redis 7.
- Отдельный пользовательский аккаунт для юзербота и отдельный бот BotFather для админки. Один и тот же Telegram-аккаунт для обоих процессов не используется.

## Секреты

Скопируйте `.env.example` в `.env`. В репозиторий попадает только пример.

`SESSION_STRING` — критичный секрет. Это полная сессия пользовательского аккаунта. Кто имеет строку, входит в аккаунт без пароля. Не коммитьте её, не кладите в логи и не передавайте в чатах.

`MASTER_KEY` — 32 случайных байта в base64. Потеря ключа делает историю нечитаемой. Смена ключа не расшифровывает старые записи.

```bash
python -c "import os,base64; print(base64.b64encode(os.urandom(32)).decode())"
```

### API ID и API HASH

1. Войдите на https://my.telegram.org под аккаунтом, который будет юзерботом.
2. Откройте API development tools и создайте приложение.
3. Запишите `API_ID` и `API_HASH` в `.env`.

### SESSION_STRING

Из каталога проекта, с заполненными `API_ID` и `API_HASH`:

```bash
python -m userbot.generate_session
```

Скрипт спросит номер телефона и код. Строку из stdout запишите в `SESSION_STRING`. Это интерактивная команда, её запускают на своей машине, не в контейнере без TTY.

`MTPROTO_TRANSPORT=direct` оставляет обычный TCP Pyrogram. `websocket` нужен, когда дата-центр на 80/443 отвечает на MTProto страницей HTTP вместо протокола: юзербот открывает официальный `wss://<dc>.web.telegram.org/apiws` и гоняет по нему обфусцированный байтовый поток. `DEVICE_MODEL`, `SYSTEM_VERSION` и `APP_VERSION` уходят в `initConnection`. Для уже существующей сессии Telegram Desktop их оставляют такими, какими сессия была создана.

### Токен админ-бота

В @BotFather создайте нового бота и запишите токен в `BOT_TOKEN`.

## Первый супер-админ

Задайте в `.env`:

```text
SUPERADMIN_TELEGRAM_ID=123456789
SUPERADMIN_DISPLAY_NAME=Имя
```

При старте `admin_bot` запись создаётся, если её ещё нет: пустая зашифрованная анкета, `is_superadmin=true`, `is_active=true`. Повторный старт не плодит дубликаты. Этот человек пишет боту `/start` и добавляет остальных операторов кнопкой «Операторы». Ручной SQL для анкеты не нужен: шифротекст привязан к UUID оператора.

`AI_REPLIES=true` и `OPENROUTER_API_KEY` включают ответ OpenRouter. Пока встреча не закреплена за оператором, модель договаривается о городе и времени и не называет телефон или точный адрес. После подтверждения звонком она отвечает уже от лица анкеты этого оператора. Модель задаётся `OPENROUTER_MODEL` (по умолчанию `google/gemini-3.5-flash`). Запрос фото, видео или кружка в модель не уходит: его закрывает альбом оператора, который забрал заказ.

Клиент пишется в `clients` с Telegram id, username и телефоном — тем, что уже есть. Оператор хранит в зашифрованной анкете телефон, ссылки на сообщение-анкету, фото, кружок и видео, и примерный адрес. Статус «свободен / занят / не работаю» пишется в `operator_statuses` и в Redis. Встреча живёт в `meetings`: обсуждение, условная договорённость (город и примерное время), ожидание подтверждения клиента, номер отправлен, подтверждена звонком, выполнена или отменена.

Как только известны город и время, свободные операторы получают в админ-боте кнопку «Принять». Первый успешный запрос забирает заказ, юзербот отправляет примерный адрес из анкеты. «Перенести» и «Отменить» пишут клиенту обычным текстом. Когда клиент подтверждает встречу, он получает телефон из анкеты. Кнопка «Подтвердил звонком» ставит оператору «🔴 Занят». «Завершить встречу» не меняет статус само: оператор снова выбирает его стрелками. Несколько клиентов идут параллельно, заказ берётся одним условным обновлением строки.

## Запуск

Из каталога репозитория, когда `.env` заполнен:

```bash
docker compose up --build
```

Сервисы: `postgres`, `redis`, одноразовый `migrate` (`alembic upgrade head`), затем `userbot` и `admin_bot`. Каталог проекта смонтирован в `/app` для разработки.

`AUTO_ASSIGN=true` ведёт клиента через встречу: оператор появляется, когда нажимает «Принять». `AUTO_ASSIGN=false` оставляет ручной показ анкеты с кнопками «Выбрать» и «Другой». `ALL_OPERATORS_BUSY_TEXT` используется только в этом ручном режиме, когда свободных нет.

Проверка миграций без запуска ботов:

```bash
docker compose up postgres redis migrate
```

## Тесты

Нужны Python 3.12 и Redis на `127.0.0.1:6379`. Тесты роутинга и сценария назначения используют базу Redis `15` и очищают только её. PostgreSQL для unit-тестов не требуется: сценарий назначения идёт через SQLite в памяти, чтобы не поднимать отдельный сервер. Боевой код ходит в PostgreSQL через asyncpg.

```bash
python -m pip install -e ".[dev]"
pytest
mypy
```

Покрыты шифрование и изоляция ключей операторов, round-robin с атомарным захватом в Redis, запрет расшифровки в репозиториях и сценарий «клиент написал → выбран свободный оператор → клиенту ушла анкета → чужой оператор историю не читает».

## Модель доступа

- Репозитории принимают и отдают `*_ciphertext` как байты и не вызывают расшифровку.
- Чужая история не выбирается: `messages` и `clients` для экрана оператора фильтруются его `operator_id`.
- Супер-админ видит имена, Telegram ID и статус Redis. Анкету и переписку он не расшифровывает.
- Отдельного вызова «расшифровать всех» нет. Ключ оператора — HKDF от `MASTER_KEY` и `operator_id`.
- В логи не пишутся текст сообщения, анкета, сессия и мастер-ключ.
